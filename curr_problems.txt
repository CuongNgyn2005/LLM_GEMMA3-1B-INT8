# CẬP NHẬT 15-07-2026 — C0 V27: ZDMA `BYTE_CNT_OVRFL`, BẢN VÁ HOST V28 CHỜ XÁC NHẬN TRÊN BOARD

## Trạng thái mới nhất

Lần C0 mới nhất dùng host `zcu104-gemma3-q8-v27-zdma-done-gated-trace`,
`FPGA_CONTRACT_CHECK=364`, `FPGA_CONTRACT_ABORT=1`, `FPGA_CONTRACT_RAW_REPAIR=0`
và `FPGA_CONTRACT_RAW_RETRY=0`. Kết quả có ý nghĩa quan trọng:

- Các `CONTRACT_VALUE_PASS` đã hoàn tất cho toàn bộ Q8 GEMV của layer 0--3 và
  `blk.4.attn_q/k/v/output.weight`; tất cả có `max_abs=0`, `max_rel=0`.
  Như vậy tại các phép đã chạy, raw INT32 từ VPU, layout packed Q8_0, đọc RESULT
  và CPU dequantize hiện khớp CPU reference tuyệt đối.
- C0 không dừng vì `RAW_MISMATCH`. Nó dừng trong `blk.4.ffn_gate.weight`
  (`K=1152, N=6912, M=5`) khi ZDMA copy RESULT từ `0xA0200000` về
  `0x800200000`, 36,864 byte:

  ```text
  status=0x00000002 state=2 isr=0x00000008 ctrl2=0x00000001
  ```

  Bit ISR `0x8` là `BYTE_CNT_OVRFL`; đây không phải thông báo model, lỗi sampler
  hay raw-result mismatch. Kênh ZDMA báo lỗi trước khi host nhận được tile RESULT.
- Với các FFN stage đã pass, ba cost lớn vẫn là `host_result_unpack` khoảng
  148.8 ms, `ip_compute` khoảng 139.4 ms và `prep` khoảng 127.5 ms cho M=5.
  Không tối ưu/pipeline các cost này trước khi C0 đi qua toàn bộ numerical gate;
  nếu không sẽ làm khó phân biệt lỗi driver với sai số mới.

## Nguyên nhân khả dĩ và sửa chữa v28

`ZDMA_CH_TOTAL_BYTE` là bộ đếm theo *channel*, không thuộc riêng descriptor.
Thanh ghi này là write-the-count-to-clear (WTC); API standalone chính thức
`XZDma_TotalByteClear()` cũng đọc giá trị rồi ghi lại chính giá trị đó. Host v27
không quản lý bộ đếm này, nên số byte có thể tích luỹ từ các transfer trước hoặc
trạng thái cũ của channel và cuối cùng kích hoạt `BYTE_CNT_OVRFL`.

`BASIC_SOC_COURSE.../FPGA_Driver.c` là reference tốt cho base address và linear
descriptor, nhưng struct của nó che vùng `0x168..0x188` bằng `dmy1[9]` và driver
one-shot không bao giờ WTC-clear `TOTAL_BYTE`. Không sao với demo transfer ngắn;
không thể dùng nguyên xi cho chuỗi hàng nghìn ACT/WEIGHT/RESULT transfer của LLM.

`fpga_host.cpp` v28 thực hiện các thay đổi có chủ đích sau:

1. Mô tả đúng các thanh ghi ZDMA `CUR_PYLD`, `CUR_DSCR` và `TOTAL_BYTE` tại
   offset `0x188`, có `static_assert` để chặn sai lệch struct/register map.
2. Xoá `TOTAL_BYTE` theo WTC sau init và **trước mỗi descriptor transfer**;
   không thay đổi bất kỳ địa chỉ ACT/WEIGHT/RESULT hay giao thức RTL nào.
3. Coi `BYTE_CNT_OVRFL` và `DMA_PAUSE` là lỗi fatal; log giải mã tên từng bit.
4. Khi transfer fail, dump 24 transfer gần nhất, gồm source/destination physical
   address, số byte, ISR/status/CTRL2, byte counter trước/sau xoá, VPU
   status/progress, current payload address và cả descriptor words.

Đây là sửa driver PS/ZDMA; **không thay RTL và không chạy synthesis/implementation**
trong cập nhật này. RTL canonical đã được đọc để đối chiếu map:
`ACT 0x00010000`, `WEIGHT 0x00100000`, `RESULT 0x00200000`; các giá trị này khớp
với địa chỉ trong C0. XSim không cần chạy lại khi RTL không đổi.

## Tiêu chí xác nhận bắt buộc trên ZCU104

Sau khi build `build_mem`, chạy lại đúng C0. Log phải có cả:

```text
ready version=zcu104-gemma3-q8-v28-zdma-bytecounter-trace
ZDMA byte-counter policy clear=before_every_transfer
```

Mốc pass tối thiểu là đi qua `blk.4.ffn_gate.weight` mà không có
`BYTE_CNT_OVRFL`. Nếu còn lỗi, giữ nguyên C0; log v28 sẽ có
`DMA_TRACE_BEGIN reason=transfer_completion_failure` và `total_before_clear` /
`total_after` để phân biệt counter stale với lỗi mới trên AXI/ZDMA. Chưa được
chuyển primary command sang FPGA raw hoặc bật weight cache lớn cho đến khi C0
qua numerical gate và lỗi transfer này được giải quyết.

Tài liệu đối chiếu: AMD ZDMA `TOTAL_BYTE` register, Xilinx standalone ZDMA API,
và Linux `zynqmp_dma` driver (ISR bit `BYTE_CNT_OVRFL`).

## 3. Phân tích định lượng một decode token

Đã phân tích các token hoàn chỉnh `seq=14..58`. Mỗi token có đúng 183 Q8 GEMV.
Các token ổn định, không có xu hướng `ip_compute_ms` tăng dần theo sequence.

### 3.1. Trung bình trên một token decode

| Stage | Thời gian trung bình | Tỷ lệ xấp xỉ |
|---|---:|---:|
| Preparation | 3.631,82 ms | 29,9% |
| DMA input | 422,60 ms | 3,5% |
| IP compute | 3.501,20 ms | 28,8% |
| DMA output | 345,61 ms | 2,8% |
| Host result unpack | 3.738,54 ms | 30,7% |
| Host scale/accumulate/store | 515,66 ms | 4,2% |
| Tổng stage FPGA | 12.161,22 ms | gần 100% token |

Traffic trung bình mỗi token:

| Loại | Dung lượng |
|---|---:|
| Weight payload DDR -> IP | 953,44 MiB |
| Raw INT32 RESULT IP -> DDR -> CPU | 119,18 MiB |
| F32 output thực sự cần cho toàn bộ GEMV | khoảng 2,752 MiB |
| Raw-result amplification | **43,31 lần** |
| VPU/ZDMA jobs | khoảng **3.234 job/token** |

### 3.2. Tensor tốn thời gian nhất

Với token `seq=58`:

| Nhóm tensor | VPU runs | Thời gian | Tỷ lệ token |
|---|---:|---:|---:|
| `token_embd.weight` / vocab projection | 1.024 | 3.661,52 ms | 30,1% |
| 26 x `ffn_down` | 520 | 2.541,41 ms | 20,9% |
| 26 x `ffn_gate` | 702 | 2.511,20 ms | 20,7% |
| 26 x `ffn_up` | 702 | 2.510,81 ms | 20,7% |
| Attention projections còn lại | phần còn lại | khoảng 0,9 s | 7,6% |

`token_embd.weight` có shape:

```text
K=1152, N=262144, M=1
weight_bytes = 301.989.888 byte
result_bytes = 37.748.736 byte
```

Một tensor này đã tạo 1.024 tile row và chiếm khoảng 30% latency/token. Đây là
output projection tạo logits, nên cũng là tensor correctness quan trọng nhất.

### 3.3. Mô hình khả năng đạt 2,5 token/s

Gemma 3 1B cần xấp xỉ 1 tỷ MAC mỗi decode token. Để đạt 2,5 token/s cần tối
thiểu khoảng 2,5 GMAC/s sustained, chưa tính attention, norm và scheduler.

PMAU hiện có 16 INT8 multiplier. Peak lý thuyết ở 187,5 MHz:

```text
16 MAC/cycle x 187,5 MHz = 3,0 GMAC/s
```

IP compute thực tế:

```text
~1,0 GMAC / 3,50 s = ~0,286 GMAC/s
```

Hiệu suất compute chỉ khoảng 9,5% peak. Single PMAU 16 lane chỉ có thể đạt mục
tiêu 2,5 token/s nếu utilization trên 83% và mọi overhead gần bằng 0; điều này
không đủ margin thực tế. Kiến trúc cần tối thiểu hai row-PE sau khi continuous
stream đã hoạt động.

Ngoài compute, weight INT8 đã là gần 953 MiB/token. Ở 2,5 token/s cần trên
2,38 GiB/s weight payload sustained. Log hiện đo khoảng 2,2–2,3 GiB/s qua ZDMA.
Vì vậy 2,5 token/s không thể đạt bằng cách chỉ thêm DSP; còn phải tăng hiệu quả
DDR/ZDMA hoặc giảm traffic/transaction overhead.

Self-test basic/packed/row-limit chỉ chứng minh:

- register map đọc/ghi được;
- ZDMA chuyển được pattern nhỏ;
- VPU tính đúng một số dot-product integer nhỏ;

Nó không chứng minh:

- 183 tensor Q8_0 của Gemma đều đúng;
- mọi block scale `d_a * d_w` đúng;
- row/block ordering của output projection đúng;
- `dst` F32 có stride/layout đúng;
- logits 262.144 phần tử là finite và khớp CPU;
- token top-1/top-k khớp reference.

## 5. Bottleneck trong `fpga_host.cpp`

### 5.1. Preparation pack lại gần 1 GiB weight mỗi token

Đường raw hiện tại trong `fpga_dma_run_q8_group()`, vùng gần dòng 2996–3260:

1. lặp `row`;
2. lặp `group block`;
3. lặp 2 beat/block;
4. đọc `block_q8_0` từ model mmap;
5. pack 16 byte qua `write_i8x16_to_ddr()`;
6. mỗi beat thực hiện bốn volatile 32-bit stores vào DDR UIO mapping.

Đây là lý do preparation khoảng 3,63 s/token.

`weight_cache=0` nên code này lặp lại cho mọi token dù weight bất biến.

#### Hướng sửa cụ thể

File: `llama.cpp/ggml/src/ggml-cpu/fpga_host.cpp`.

1. Giữ `WEIGHT_CACHE_BASE=0x01000000` và chỉ map trong reserved `ddr_high` đã
   được device-tree/UIO xác nhận.
2. Bật cache theo budget hữu hạn, đủ chứa payload Q8 đã pack. Log hiện đo
   953,44 MiB/token; budget thử nghiệm nên 1.100 MiB, vẫn dưới cửa sổ 2 GiB.
3. Build cache trong warmup/prefill, để decode chỉ dùng `tile.ddr_off` làm source
   ZDMA; không copy model weight bằng CPU lần nữa.
4. Sau khi diagnostic pass, đổi cache từ opt-in thành default-on khi UIO
   `ddr_high` quảng bá đủ size; giữ `FPGA_WEIGHT_CACHE_DISABLE=1` làm opt-out.
5. Nếu reserved region nhỏ hơn budget, fail init rõ ràng; không fallback sang
   `/dev/mem` và không map vượt UIO size.

#### Lỗi hiệu năng trong cache hiện có phải sửa trước khi bật

`validate_weight_cache_entry()` gần dòng 2407 hiện tính lại CRC của **toàn bộ
payload tensor trên mỗi cache hit**:

```cpp
fpga_crc32_ddr(entry->base_off, entry->bytes)
```

Nếu bật nguyên trạng, CPU sẽ đọc lại gần 1 GiB DDR mỗi token chỉ để CRC và có
thể tạo bottleneck mới ngang preparation.

Sửa thành:

- CRC một lần sau build;
- CRC một lần khi attach/recover cache ở process start;
- mỗi hit chỉ kiểm tra header O(1), generation/epoch, tensor ID và bounds;
- thêm `entry.validated_generation`;
- chỉ full-CRC lại khi `FPGA_WEIGHT_CACHE_VERIFY=1`.

Expected result: `weight_cache_hits` đạt gần toàn bộ 183 tensor trong decode,
`weight_cache_misses=0` sau warmup, preparation giảm mạnh mà không quét DDR bằng
CPU mỗi token.

### 5.2. Activation quantization

`ensure_quantized_activation_matrix()` quantize F32 activation thành Q8_0 cho
mỗi matmul. Decode `M=1` nên khối lượng này nhỏ hơn weight packing, nhưng vẫn
nằm trong preparation.

Không bật lại pointer-only activation cache. GGML tái sử dụng buffer nên cùng
pointer không đảm bảo cùng nội dung. Cache activation chỉ hợp lệ nếu key có:

```text
tensor pointer + data pointer + shape/stride + graph generation + seq_pos +
content/version counter
```

Ưu tiên đúng là SPU tạo và giữ activation Q8_0 on-chip, sau đó forward trực tiếp
sang VPU; không phải cache pointer trên CPU.

### 5.3. Host result unpack đọc non-cacheable DDR theo từng word

`ddr_read_i32x4()` gần dòng 737:

```cpp
volatile const uint32_t * src = ...;
for (int w = 0; w < 4; ++w) out[w] = src[w];
```

Sau đó `fpga_dma_run_q8_group()` lặp từng 128-bit RESULT word, copy bốn lane vào
`std::vector<int32_t> partial`.

119,18 MiB raw result tốn 3,74 s, chỉ khoảng 31,9 MiB/s CPU read. Đây không phải
giới hạn của ZDMA; đây là CPU đọc non-cacheable/UIO mapping bằng volatile scalar
loads rồi copy lần hai.

#### Fix tạm thời

Chỉ dùng khi chưa có PL-scale:

1. Xác nhận mapping `ddr_high` là Normal Non-cacheable hoặc DMA-coherent, không
   phải Device memory cấm vector/burst load.
2. Sau DMA completion và acquire fence, bulk-copy cả range sang cached vector
   bằng routine 128-bit/NEON hoặc `memcpy` đã benchmark.
3. Không gọi helper cho từng 16 byte.
4. Gộp unpack và CPU accumulate để không ghi rồi đọc lại `partial`:
   đọc block 128-bit, convert bốn raw values và cộng ngay vào accumulator.
5. Nếu mapping không cho bulk read an toàn, dùng `dma-buf`/`udmabuf` có explicit
   CPU-device sync thay vì bỏ `volatile` tùy tiện.

Expected result tạm thời: tăng read bandwidth ít nhất vài trăm MiB/s. Tuy nhiên
đây không phải kiến trúc cuối vì 119 MiB/token vẫn là traffic vô ích.

#### Fix triệt để

VPU raw stream phải đi thẳng sang SPU scale accumulator. CPU chỉ đọc một final
F32/Q16.16 value mỗi output row:

```text
119,18 MiB raw/token -> khoảng 2,752 MiB final F32/token
```

Giảm traffic tối thiểu 43,31 lần và loại bỏ `partial` cùng hai vòng CPU
scale/accumulate.

### 5.4. CPU scale/accumulate vẫn nằm trong critical path

Vùng gần dòng 3464–3474 thực hiện:

```cpp
accum[row] += raw * act_scale * weight_scale;
```

Đây là contract đúng cho Q8_0, nhưng tốn khoảng 516 ms/token và buộc raw result
phải về PS. Sau khi PL-scale pass numerical contract, xóa đường này khỏi primary
inference; chỉ giữ làm golden reference diagnostic.

### 5.5. Mỗi tile là một chuỗi blocking hoàn toàn

Đường raw hiện tại:

```text
CPU pack -> ACT DMA -> WEIGHT DMA -> START -> busy poll -> RESULT DMA
-> CPU unpack -> CPU accumulate -> tile kế tiếp
```

Khoảng 3.234 job/token gây hàng nghìn lần program/poll ZDMA và VPU. Không có
overlap preparation, transfer, compute và drain.

### 5.6. Global mutex

`fpga_try_matmul_extended()` khóa `g_mutex` từ trước GEMV đến sau toàn bộ GEMV.
Điều này serial hóa mọi FPGA matmul. GGML graph có dependency nên không phải
bottleneck P0, nhưng về sau mutex phải chỉ bảo vệ register submission/queue;
không được giữ trong toàn bộ compute nếu hardware có job queue.

## 6. Ping-pong hiện có nhưng chưa hoạt động hiệu quả

### 6.1. Trạng thái hiện tại

| Thành phần | Có trong source | Có hoạt động trên run board |
|---|---:|---:|
| Hai bank ACT | Có | Không dùng scheduler |
| Hai bank WEIGHT | Có | Không dùng scheduler |
| Hai bank RESULT | Có | Không dùng scheduler |
| Descriptor/job ID | Có | Capability có, scheduler khóa |
| Host `slots[2]` | Có | Không gọi vì `pl_scale=0` |
| VPU -> SPU ready/valid | RTL local có | Board protocol/id bằng 0 |
| PL scale accumulation | RTL local có | `pl_scale=0` |

Kết luận: primary run hiện tại **không có ping-pong thực tế**.

### 6.2. Scheduler host hiện tại chưa phải full overlap

Ngay cả khi bật, `fpga_hw_q8_0_matmul_dma_to_ip_pipelined()` hiện làm:

```text
prepare B trên CPU
wait_and_drain A
submit B
accumulate A
```

Nó overlap được CPU preparation B với compute A và CPU accumulate A với compute
B. Nhưng nó chưa overlap:

- input DMA B với compute A;
- output DMA A với compute B;
- scale DMA B với compute A.

Nguyên nhân: `wait_and_drain()` thực hiện RESULT/SPU_OUT DMA trước khi
`submit()` job tiếp theo. Ngoài ra DDR staging ACT/WEIGHT/RESULT đang dùng cùng
offset cho cả hai slot, nên chưa thể có hai job ở trạng thái DMA/ready độc lập.

### 6.3. Ping-pong đúng cần hai tầng bank

Không chỉ local RAM trong PL, mà DDR staging ở host cũng cần hai slot.

Đề nghị tách offset DDR khỏi địa chỉ LMM/IP. Ví dụ bố trí trong 4 MiB scratch
đang map, sau khi kiểm tra overlap bằng `range_fits`:

| Vùng DDR staging | Slot 0 | Slot 1 | Dung lượng tối đa |
|---|---:|---:|---:|
| ACT | 0x000000 | 0x001000 | 2 KiB/slot |
| WEIGHT | 0x010000 | 0x090000 | 512 KiB/slot |
| SCALE | 0x110000 | 0x120000 | 64 KiB/slot |
| RESULT | 0x130000 | 0x140000 | 64 KiB/slot |

Các offset trên chỉ là layout đề nghị cho DDR reserved scratch; destination
LMM vẫn là `ACT_BASE=0x10000`, `WEIGHT_BASE=0x100000`, v.v. Không dùng cùng một
constant cho cả DDR source và IP destination nữa.

### 6.4. FSM ownership bắt buộc

Mỗi slot phải có state:

```text
FREE
 -> CPU_PACKING
 -> INPUT_DMA
 -> READY
 -> COMPUTING
 -> RESULT_READY
 -> OUTPUT_DMA
 -> CPU_CONSUME
 -> FREE
```

Metadata mỗi slot:

```text
job_id, tensor_id, token_id, row0, rows, k_block0, group_blocks,
format, input_bytes, result_bytes, bank, valid, error, generation
```

Quy tắc consistency:

- CPU chỉ ghi DDR slot ở `FREE/CPU_PACKING`;
- ZDMA input chỉ đọc slot ở `INPUT_DMA`;
- VPU chỉ compute local bank ở `COMPUTING`;
- host chỉ drain đúng `{done_job_id, done_bank}`;
- bank chỉ trở về FREE sau drain/consume ack;
- timeout phải log cả owner/state/job của hai slot;
- mọi transition phải có assertion trong testbench.

### 6.5. Timeline full overlap với một ZDMA

Vì chỉ có một ZDMA, input và output DMA không chạy đồng thời với nhau. Tuy nhiên
DMA vẫn có thể chạy đồng thời với VPU compute:

```text
Thời gian    CPU                  ZDMA                    VPU
t0           pack A               idle                    idle
t1           pack B               input A                 idle
t2           chuẩn bị descriptor  input B                 compute A
t3           consume A            output A                compute B
t4           pack C               input C                 compute B/A-next
```

Scheduler phải ưu tiên không để VPU đói:

1. khi compute A bắt đầu, DMA input B ngay;
2. chỉ drain A sau khi B đã READY hoặc B đã start;
3. trong khi compute B, drain A rồi pack/input C;
4. nếu result FIFO gần đầy, output DMA được ưu tiên để tránh deadlock.

### 6.6. File cần sửa cho ping-pong

`fpga_host.cpp`:

- tách `fpga_submit_q8_tile_job()` thành:
  - `fpga_stage_cpu(slot)`;
  - `fpga_dma_input(slot)`;
  - `fpga_start_compute(slot)`;
  - `fpga_poll_done(slot)`;
  - `fpga_dma_output(slot)`;
  - `fpga_consume(slot)`;
- tạo scheduler event loop hai slot;
- dùng source DDR offset theo slot;
- không giữ global mutex trong thời gian compute;
- ghi timestamp transition và occupancy.

`AXI4_Mapping.v`:

- descriptor phải per-bank, không chỉ một bộ register global;
- thêm commit/claim/release atomically;
- status trả `{slot_state, active_job, done_job, error}`;
- register write vào descriptor B không được thay metadata đã latch của A.

`Matrix_Vector_Multiplication.v`:

- local ACT/WEIGHT/RESULT đã có hai bank;
- thêm assertion không write active bank;
- result bank chỉ publish sau final write commit;
- start chỉ claim bank ở READY.

`tb_Matrix_Vector_Multiplication.v` hoặc testbench tương ứng:

- randomize preparation, DMA-model và compute latency;
- test A compute trong lúc B fill;
- test A drain trong lúc B compute;
- test job ID wrap, timeout, stale done và backpressure.

Theo AMD UG1399, PIPO bảo đảm chứa trọn một iteration và phù hợp random access;
FIFO phù hợp stream tuần tự nhưng depth sai có thể full/empty stall hoặc deadlock.
Thiết kế này cần PIPO cho ACT/WEIGHT/RESULT bank và FIFO cho raw result stream.

## 7. Bottleneck trong RTL

### 7.1. PMAU chính đã pipeline, nhưng controller phá throughput

`PMAU_Full.v` có:

- 16 `mult_gen_0` INT8 x INT8;
- multiplier latency 3;
- adder tree 4 tầng, mỗi tầng có register;
- accumulator và result FIFO.

PMAU có thể nhận gần một beat/cycle sau khi fill. Vấn đề nằm ở
`Matrix_Vector_Multiplication.v` raw mode:

- một Q8 block có 2 beat;
- `wait_after_feed = feed_last_r` trong raw mode;
- sau beat thứ hai, FSM chuyển `S_WAIT_RESULT`;
- flush read pipeline;
- chờ PMAU result;
- ghi RESULT;
- phát raw token sang SPU;
- giữ `S_RAW_STREAM_HOLD` đến khi SPU ready;
- sau đó mới chạy block tiếp theo.

Với hàng nghìn row/block, pipeline bị fill/drain lại sau mỗi 32 phần tử. Đây là
nguyên nhân chính khiến IP chỉ đạt khoảng 9,5% peak.

### 7.2. Fix RTL P1: continuous raw-block issue/retire

File: `DATN_RTL/RTL/Matrix_Vector_Multiplication.v`.

Thay một FSM tuần tự bằng hai pipeline decoupled:

```text
Issue engine:
  address -> BRAM read -> PMAU input

Retire engine:
  PMAU result -> metadata FIFO -> RESULT writer/SPU stream
```

Yêu cầu chi tiết:

1. Không chuyển `S_WAIT_RESULT` sau mỗi `feed_last`.
2. `feed_last` chỉ đánh dấu boundary block cho PMAU accumulator.
3. Issue engine tiếp tục block/row kế tiếp nếu:
   - read pipeline còn chỗ;
   - PMAU input ready;
   - metadata/result FIFO chưa gần full.
4. Khi phát last beat của block, push metadata
   `{row, block, group_blocks, last_block, clear, job, bank}` vào context FIFO.
5. Retire engine pop context đúng lúc `pmau_result_valid`.
6. RESULT BRAM writer và SPU raw stream chạy độc lập; backpressure chỉ dừng issue
   khi FIFO đạt high-watermark, không flush cả pipeline.
7. `done` chỉ assert khi:
   - mọi beat đã issue;
   - PMAU inflight bằng 0;
   - context FIFO empty;
   - result FIFO empty;
   - SPU đã accept final token;
   - final memory write đã commit.

Depth ban đầu nên đủ một burst, ví dụ 64 hoặc 128 context. Sau simulation random
stall mới giảm depth dựa trên occupancy, đúng khuyến nghị AMD.

Expected result: raw result có thể xuất gần một block mỗi 2 cycle thay vì một
block mỗi chuỗi fill/wait/drain dài.

### 7.3. Bypass dequant multiplier khi chạy raw mode

Trong `PMAU_Full.v`, dù scale bằng `FP16_ONE` và output cuối chọn raw, datapath
vẫn thực hiện wide multiply ở `deq_s2_mul` rồi mới bypass.

Sửa:

- tách raw FIFO input trực tiếp từ `row_commit` qua một register;
- chỉ enable dequant multiplier khi mode thực sự yêu cầu scale;
- propagate valid/last riêng;
- tăng result FIFO depth để hấp thụ burst continuous.

Expected result: giảm latency block, giảm switching power và loại DPOP warning
ở multiplier không cần dùng trong raw mode.

### 7.4. SPU scale accumulator có throughput thấp hơn producer

`SPU_Q8_Scale_Accum.v` xử lý một raw entry qua 7 state:

```text
IDLE -> SCALE -> PRODUCT_MUL -> CLAMP -> RAW_MUL -> CONTRIB -> ACCUM
```

Nó chỉ accept entry mới khi trở về IDLE. Trong khi continuous PMAU có thể sinh
một raw block mỗi 2 cycle. FIFO depth 32 chỉ trì hoãn stall; không sửa mismatch
throughput.

Ngoài ra module dùng 64x64 và 32x65 multiply. Synthesis log khuyến nghị thêm
16 và 8 pipeline register cho wide multiplier; DRC còn nhiều DPIP/DPOP warning.

### 7.5. Fix RTL P2: pipelined scale engine II <= 2

Ưu tiên block-major/row-major scheduling:

```text
block 0: row 0, row 1, ... row 255
block 1: row 0, row 1, ... row 255
...
```

Như vậy hai lần update cùng một row cách nhau hàng trăm entry, loại hazard
read-after-write trong accumulator BRAM và cho phép pipeline sâu.

Tạo `SPU_Q8_Scale_Pipeline.v`:

```text
S0 latch raw,row,flags,scale
S1 FP16 -> fixed conversion
S2 product scale DSP stage
S3 raw x combined-scale DSP stage
S4 shift/round/saturate
S5 accumulator BRAM read
S6 add
S7 accumulator BRAM write/output
```

Mỗi stage giữ `valid,row,block,last,clear,job,bank`.

Hai phương án scale:

1. Giữ `d_a` và `d_w` FP16 trong PL, pipeline multiplier đúng chuẩn;
2. Host/SPU quantizer tạo trước `combined_scale = d_a*d_w` ở format đã thống
   nhất, giảm một wide multiply mỗi raw entry.

Phương án 2 chỉ được dùng sau bit-accurate reference trên toàn dải scale của
model. Không dùng global shift thay scale per block.

Target initiation interval: II=2 hoặc II=1. Nếu một pipeline chưa đủ, instantiate
2–4 lane scale và phân phối row độc lập.

### 7.6. Row parallelism: dùng DSP dư đúng cách

Report cho thấy DSP chỉ dùng 81/1728. Sau continuous stream, thêm parameter:

```verilog
parameter integer ROW_PE = 2;
```

Kiến trúc ROW_PE=2:

- broadcast cùng activation beat cho hai PMAU;
- đọc weight của hai row mỗi cycle;
- hai adder tree/accumulator độc lập;
- phát hai raw results kèm row ID;
- peak compute = `2 x 16 x 187,5 MHz = 6,0 GMAC/s`.

Không được duplicate toàn bộ weight RAM. URAM hiện dùng 64/96. Duplicate ngây
thơ sẽ cần khoảng 128 URAM và không fit.

Phải partition weight theo row lane:

```text
lane = row % ROW_PE
local_row = row / ROW_PE
address = local_row * active_col_beats + beat
```

Mỗi row lane sở hữu nhóm URAM riêng; tổng payload logic không đổi, chỉ thay
banking/fragmentation. Bắt đầu ROW_PE=2, lấy utilization mới do người dùng chạy,
sau đó mới quyết định ROW_PE=4.

Files cần sửa:

- `Matrix_Vector_Multiplication.v`: generate row lanes, issue/retire metadata;
- `PMAU_Full.v`: instantiate theo generate ở GEMV hoặc tạo wrapper `PMAU_Array`;
- `Dual_Port_BRAM.v`: hỗ trợ layout row-partition, giữ output register;
- testbench: random dimensions, odd last row, lane mapping, two simultaneous
  results, backpressure.

### 7.7. Không ưu tiên tăng NUM_LANES lên 32 ngay

NUM_LANES=32 yêu cầu 256-bit weight/activation mỗi cycle, trong khi local port
và AXI datapath hiện là 128-bit. Việc này buộc thay address map hoặc dùng hai
read port/beat, làm phức tạp ping-pong fill. ROW_PE=2 giữ giao thức 128-bit và
tận dụng activation broadcast, phù hợp hơn cho bước đầu.

### 7.8. Vocab projection cần đường riêng

`token_embd.weight` chiếm 30,1% token. Các bước:

1. Bắt buộc numerical contract cho tensor thứ 183.
2. PL-scale để output chỉ còn 262.144 F32 = 1 MiB, thay vì 36 MiB raw partial.
3. ROW_PE=2 để giảm compute row projection.
4. Sau khi full logits đúng, có thể thêm streaming top-k 40 trong PL:
   - mỗi row logit đi qua comparator tree;
   - giữ top-40 `{id,value}`;
   - CPU chỉ nhận top-k thay 1 MiB logits.

Top-k PL đòi hỏi thay integration sampler vì GGML hiện mong full F32 `dst`.
Không làm bước này trước khi full-logits mode pass reference.

## 8. Khả năng lưu trữ và reuse của SPU

### 8.1. Hiện trạng

`SPU_Local_Memory.v` có bốn vùng độc lập:

```text
SPU_IN, SPU_OUT, SPU_PARAM, SPU_SCRATCH
WORD_DEPTH = 4096, width = 128 bit
```

Mỗi vùng chứa 64 KiB, tổng payload danh nghĩa 256 KiB. Hiện chưa có bank
ownership/residency directory cho tensor sống qua nhiều command. Board hiện
cũng không bật các SPU op trong inference (`spu_silu/rms/rope/softmax=0`).

### 8.2. Resource headroom

Report placed mới nhất:

| Resource | Used | Available | Tỷ lệ |
|---|---:|---:|---:|
| LUT logic | 15.174 | 230.400 | 6,59% |
| FF | 21.570 | 460.800 | 4,68% |
| BRAM tile | 104,5 | 312 | 33,49% |
| URAM | 64 | 96 | 66,67% |
| DSP48E2 | 81 | 1.728 | 4,69% |

BRAM còn nhiều để double-buffer vector/intermediate. URAM chỉ còn 32 block,
không đủ giữ model 1 GiB và không được dùng để duplicate toàn bộ weight banks.

### 8.3. Data nên giữ on-chip

Ưu tiên theo lợi ích/dung lượng:

1. activation Q8_0 hiện tại và activation kế tiếp;
2. scale table của tile đang compute và tile kế tiếp;
3. partial/final accumulator theo row;
4. RMSNorm weight và RoPE parameter thường dùng;
5. gate/up intermediate cho SiLU;
6. tile KV đang active, không phải toàn KV cache.

Không thể giữ:

- toàn bộ 1B weight;
- toàn bộ KV cache 38 MiB hiện tại;
- vocab matrix 302 MiB.

### 8.4. Residency directory bắt buộc

Thêm bảng descriptor nhỏ trong BRAM/LUTRAM:

```text
valid, tensor_id, layer_id, token_id, generation,
format, length, scale_format, bank, base, bytes,
producer, consumer_count, dirty, last_use
```

SPU/VPU chỉ consume tensor khi descriptor valid và generation khớp. CPU chỉ
được overwrite khi `consumer_count=0`.

### 8.5. Kiến trúc SPU memory đề nghị

Phase đầu:

- bank đôi `SPU_IN[2]` và `SPU_OUT[2]`;
- giữ `SPU_PARAM` persistent theo layer/tensor ID;
- `SPU_SCRATCH` partition thành accumulator, softmax scratch và descriptor;
- output SPU có direct-forward port sang ACT input VPU;
- CPU readback chỉ khi graph cần F32 ở PS hoặc debug.

Với BRAM còn khoảng 207,5 tile, tăng thêm khoảng 50–70 BRAM cho double-buffer
SPU là khả thi về budget sơ bộ. Con số cuối phải lấy từ report sau synthesis do
người dùng chạy; plan maker không tự chạy.

stage. Thiết kế weight partition phải dùng output registers/cascade hợp lý, và
không giả định một URAM cung cấp tùy ý nhiều read port.

## 10. Roadmap triển khai bắt buộc theo phase

### Phase C0 — Đóng numerical correctness

**Files:**

- `fpga_host.cpp`;
- `tools/main/main.cpp`;
- testbench VPU/SPU.

**Công việc:**

1. Deploy đúng bitstream có protocol=1/id=VPU1; xác nhận register.
2. Chạy contract 7, sau đó 182 prefill, sau đó 364 (prefill + decode); repair tắt.
3. A/B CPU-only cùng GGUF, seed, temp và prompt.
4. Thêm token/logit top-5 trace.
5. Lưu golden vector cho raw, scaled output và vocab logits.

**Gate pass:**

- raw mismatch = 0;
- value mismatch = 0;
- logits finite;
- top-5 FPGA khớp CPU trong tolerance;
- token đầu tiên khớp CPU và là text hợp lệ.

Không qua gate này thì dừng mọi performance optimization.

### Phase H1 — Weight prepack/cache an toàn

**File chính:** `fpga_host.cpp`.

1. Sửa full CRC per-hit thành validate-once/generation.
2. Enable bounded cache 1.100 MiB trong reserved UIO DDR.
3. Build cache trong warmup; decode phải 100% hit.
4. Thêm counters `cache_lookup_us`, `cache_crc_us`, `pack_us` riêng.

**Expected:** preparation giảm từ 3,63 s/token xuống còn activation/descriptor
preparation; decode không CPU-copy 953 MiB weight.

### Phase R1 — Continuous raw stream

**Files:**

- `Matrix_Vector_Multiplication.v`;
- `PMAU_Full.v`;
- VPU testbench.

1. Issue/retire decoupled.
2. Context FIFO 64/128.
3. Không wait mỗi block.
4. Raw bypass dequant multiplier.
5. Random backpressure simulation.

**Expected:** IP compute tiến gần 1 block/2 cycles, thay vì fill/drain mỗi block.

### Phase R2 — SPU scale pipeline và compact output

**Files:**

- thay/refactor `SPU_Q8_Scale_Accum.v`;
- `SPU_Top.v`;
- `SPU_Local_Memory.v`;
- `AXI4_Mapping.v`;
- host PL-scale consume path.

1. II <= 2.
2. Schedule block-major/row-major để tránh accumulator hazard.
3. Pack bốn final 32-bit output trên mỗi 128-bit word; không dùng 16 byte/row.
4. CPU không nhận raw partial.

**Expected:** result traffic giảm ít nhất 43 lần; host unpack và CPU accumulate
ra khỏi critical path.

### Phase H2 — Full ping-pong/DMA overlap

**Files:** `fpga_host.cpp`, `AXI4_Mapping.v`, GEMV RTL, testbench.

1. Hai DDR staging slot độc lập.
2. Per-bank descriptors.
3. Input B DMA trong compute A.
4. Output A DMA trong compute B.
5. Scheduler occupancy/timeline counters.

**Expected:** steady-state tile time gần:

```text
max(T_input_DMA, T_compute, T_output_DMA)
```

thay vì tổng ba thời gian.

### Phase R3 — ROW_PE=2

**Files:** GEMV, PMAU array, weight memory partition, tests.

1. Partition row, không duplicate payload.
2. Hai PMAU và hai result lanes.
3. Scale pipeline đủ throughput.
4. Giữ timing 187,5 MHz.

**Expected peak:** 6 GMAC/s, tạo margin cho mục tiêu 2,5 token/s.

### Phase R4 — Vocab optimization

1. PL-scale full logits trước.
2. ROW_PE=2 cho vocab rows.
3. Sau correctness, optional streaming top-k 40.

### Phase S1 — SPU residency/fusion

1. Bank đôi IN/OUT.
2. Persistent PARAM/descriptor.
3. Direct SPU->VPU activation forwarding.
4. Fusion RMSNorm->Quant->GEMV và SiLU->Quant->GEMV.
5. PS readback chỉ ở graph boundary bắt buộc.

## 14. Kết luận cuối

Hiện tượng chậm không phải một bottleneck đơn lẻ. Ba stage lớn gần bằng nhau:

```text
preparation ~3,63 s
IP compute ~3,50 s
host result unpack ~3,74 s
```

Ping-pong có trong source nhưng không hoạt động trên primary run; ngay cả code
scheduler hiện có cũng mới overlap CPU preparation/accumulation, chưa overlap
input/output DMA thật sự.

Điểm chết RTL lớn nhất là raw mode stop/wait sau mỗi block Q8 hai beat. Điểm
chết host lớn nhất là pack lại gần 1 GiB weight và đọc 119 MiB raw result bằng
volatile scalar load mỗi token. Điểm correctness lớn nhất là contract checker
tắt và bitstream board không khớp protocol/id local.

Đường khả thi để đạt trên 2 token/s, hướng tới 2,5 token/s là:

```text
numerical contract pass
-> weight prepack/cache không CRC mỗi hit
-> continuous PMAU raw stream
-> VPU->SPU scale accumulation, không raw round-trip
-> full two-slot DMA ping-pong
-> ROW_PE=2
-> vocab projection optimization
-> SPU on-chip residency/fusion
```

Thiếu bất kỳ mắt xích nào trong chuỗi trên thì mục tiêu 2,5 token/s khó đạt một
cách bền vững ở W8A8/Q8_0 trên ZCU104.

### 15.1. Cache 1.100 MiB không chồng Linux System RAM, nhưng chưa an toàn để dùng

Read-only preflight trên board đã xác nhận đầy đủ:

```text

```

Vì vậy `FPGA_WEIGHT_CACHE_MB=1100` không vượt resource Device Tree và không
ghi đè System RAM. Hai lần ZCU104 treo khi cache bật là bằng chứng về rủi ro

bulk write này diễn ra.

1. Từ chối `FPGA_WEIGHT_CACHE_MB > 16` trước mọi mmap DDR/cache write trừ khi

2. Không dùng cờ xác nhận đó cho đến khi cache thử dần 4 -> 16 -> 64 MiB và

### 15.7. C0 v23: FPGA raw GEMV chạy thật, lỗi nằm ở normal ZDMA sequencing

C0 v23 đã chạy với `legacy_raw_cpu_bypass=0`, `contract_check=183`,
`contract_abort=1`, raw repair tắt và cache tắt. Đây là bằng chứng FPGA GEMV
thật đã được sử dụng, không phải CPU fallback. Raw values và final F32 value
đã pass qua toàn bộ tensor từ `blk.0` đến `blk.7.ffn_up.weight`.

Lỗi đầu tiên là:

```text
tensor=blk.7.ffn_down.weight layer=7 tile=20
CONTRACT_RAW_SUMMARY ... mismatches=187 action=abort
CONTRACT_STAGING_AUDIT phase=post_result integrity=fail
```

Audit chỉ ra ACT vẫn nguyên vẹn, còn byte weight staging ở DDR sai sau normal
launch. Tuy nhiên forensic replay cùng `row=281`, `block=2` đã pass lần lượt:

```text
forensic_after_restage       integrity=pass
forensic_after_act_dma       integrity=pass
forensic_after_weight_dma    integrity=pass
forensic_after_vpu           integrity=pass
forensic_after_result_dma    integrity=pass
CONTRACT_FORENSIC_RAW got=5534 expected=5534
```

Vì replay dùng đúng payload, ZDMA, VPU, RESULT DMA và raw dot, kết quả này
loại trừ lỗi số học VPU cố định, lỗi layout Q8_0 cố định và tình trạng bitstream
hỏng toàn cục. Nó cho thấy lỗi phụ thuộc trình tự normal launch.

Host cũ kế thừa điều kiện completion `STATUS.state == 0 || state == 3` từ
`BASIC_SOC_COURSE/.../FPGA_Driver.c`. Điều kiện đó không chứng minh ownership
của descriptor đã được ZDMA nhả. Theo AMD UG1087, `ZDMA_CH_CTRL2.EN` được HW
clear khi DMA operation hoàn tất, và descriptor phải ổn định khi channel đang
enabled. Vì vậy v24 thay completion gate thành `CTRL2.EN == 0` cả trước khi
ghi descriptor mới lẫn sau khi start; đồng thời clear `ZDMA_CH_ISR` bằng
write-one-to-clear `0xFFF` trước mỗi descriptor.

v24 không thêm `sleep`, không thay đổi RTL, địa chỉ, data layout, cache hoặc
arithmetic. Nó chỉ loại bỏ một vi phạm contract xác định: host không được ghi
descriptor mới khi ZDMA còn `EN=1`. Việc sửa này có loại bỏ toàn bộ mismatch
hay không phải được xác nhận bằng C0 v24 trên board.

### 15.9. Update 15-07-2026: v29 C0 exposes a bounded-descriptor ZDMA fault candidate

The latest C0 run is not a pass. It reaches `blk.9.ffn_down.weight`, layer 9,
tile 20, then reports 160 raw mismatches and aborts. This is useful evidence:

```text
CONTRACT_RAW_MISMATCH row=475 block=46 got=-7801 expected=-7954
CONTRACT_STAGING_AUDIT phase=post_result integrity=fail
weight_first_bad=18 weight_expected=23 weight_actual=127
```

The activation staging bytes remain intact. Every immediately preceding ZDMA
trace completes with `DMA_DONE`, `CTRL2.EN=0`, `status=0`, and no ZDMA error
bits. The normal launch copies a 512 KiB WEIGHT payload. The same tile is then
restaged and replayed by the forensic path; all replay audits pass and the raw
value becomes exact:

```text
forensic_after_restage       integrity=pass
forensic_after_act_dma       integrity=pass
forensic_after_weight_dma    integrity=pass
forensic_after_vpu           integrity=pass
forensic_after_result_dma    integrity=pass
CONTRACT_FORENSIC_RAW got=-7954 expected=-7954
```

This is not proof of a fixed PMAU arithmetic, Q8_0 layout, address window,
timeout, or byte-counter failure. It is a normal-sequence-dependent
data-integrity failure. The exact board-level cause remains to be confirmed;
the remaining host-controlled suspect is a long 512 KiB ZDMA descriptor in a
long-lived sequence.

Host v30 changes only descriptor submission, not the VPU tile or arithmetic:

1. `fpga_host.cpp` caps each ZDMA descriptor at 64 KiB by default. A 512 KiB
   WEIGHT transfer becomes eight ordered contiguous copies, e.g.
   `WEIGHT[1/8]` through `WEIGHT[8/8]`. The final IP address range and all
   packed Q8 bytes are unchanged before `CTRL_START` is written.
2. `ready` records `zdma_max_transfer_bytes=65536` and the policy line records
   the active cap. On failure, the existing bounded DMA trace identifies the
   exact chunk, source, destination, byte count, completion state, and VPU
   status. No large weight cache, fusion, raw repair, or CPU fallback is
   enabled by this change.
3. The production primary command remains CPU-quarantined while the board
   reports `bitstream_id=0`; it must not be used as a raw-FPGA correctness
   result. Do not enable `FPGA_WEIGHT_CACHE`, `FPGA_FUSE_RAW_RESULT_ACCUM`,
   `FPGA_ACCELERATE_VOCAB`, or `FPGA_ALLOW_UNVERIFIED_LEGACY_RAW`.

Required board verification after building v30:

```text
ready version=zcu104-gemma3-q8-v30-zdma-bounded-descriptors
zdma_max_transfer_bytes=65536
CONTRACT_RAW_MISMATCH = 0
CONTRACT_VALUE_NONFINITE = 0
raw_mismatches=0
value_mismatches=0
```

If C0 still aborts, retain the whole trace beginning with
`CONTRACT_RAW_MISMATCH`; it will now contain `WEIGHT[x/8]` entries and directly
distinguish a faulty sub-transfer from a post-transfer source-staging change.

### 15.10. Update 15-07-2026: v30 fixes raw transport but exposes a GGML numerical-contract mismatch

The supplied v30 board log changes the failure class. ZDMA bounded descriptors
complete without an error and the raw INT32 contract has no mismatch through
`blk.9.ffn_up.weight`. C0 then aborts at `blk.9.ffn_down.weight` because 365
destination values are NaN:

```text
CONTRACT_VALUE_NONFINITE ... got=-nan expected=-nan
CONTRACT_VALUE_SUMMARY ... checked=5760 bad=365 nonfinite=365 action=abort
```

This is not a C0 pass. The old value contract computed `expected` with the same
private activation quantizer and the same host scales used to construct the
FPGA result. Therefore `max_abs=0` proved only that RTL matched the host's own
emulation. It did not prove equivalence with the ggml CPU backend.

The concrete semantic divergence was introduced by v29/v30: activation `qs[]`
were generated by a private `std::round` converter and host accumulation used
the unrounded FP32 scale. The normal ggml Q8_0 path calls the architecture-
selected `quantize_row_q8_0()`, stores each block scale in FP16, and the dot
kernel consumes that stored FP16 scale. A backend that substitutes an FP32-only
scale is numerically different and may accumulate hidden-state drift across
transformer layers.

Host v31 (`zcu104-gemma3-q8-v31-ggml-native-q8-contract`) corrects this boundary:

1. Activation conversion calls `quantize_row_q8_0()` from `ggml-cpu/quants.h`.
   This matches the AArch64 CPU backend's rounding and Q8_0 block layout.
2. Raw FPGA results are scaled with the FP16 value stored in each activation
   block, exactly as ggml does. An FP16-scale overflow is fatal; it is not
   hidden with an FP32-only scale.
3. C0 value checking calls `ggml_vec_dot_q8_0_q8_0()` for the reference. It no
   longer compares the FPGA output with a second copy of host-private math.
4. The 64 KiB descriptor cap, ZDMA `DMA_DONE && EN==0` gate, byte-counter clear,
   raw mismatch forensics, large-cache safety guard, and CPU quarantine remain
   unchanged.

Required v31 board gate:

```text
ready version=zcu104-gemma3-q8-v31-ggml-native-q8-contract
CONTRACT_VALUE_PASS ... reference=ggml_vec_dot_q8_0_q8_0
CONTRACT_RAW_MISMATCH = 0
CONTRACT_VALUE_NONFINITE = 0
ACTIVATION_SCALE_FP16_OVERFLOW = 0
raw_mismatches=0
value_mismatches=0
```

Primary inference remains CPU-quarantined while the deployed bitstream reports
protocol/id zero and before this v31 gate passes. Performance work on cache,
fusion, PL scale, ping-pong, or vocabulary projection must not be enabled yet.
